# GAME_DESIGN.md — ゲーム設計書

## 世界観

### DataCraft Agency

プレイヤーはデータエンジニアリング専門エージェンシー「DataCraft Agency」の新人エンジニア。
毎日様々な業界のクライアントから「データ課題」が届き、クエストとして受注・解決する。

```
「ようこそ、DataCraft Agencyへ。
ここでは毎日、様々なクライアントからデータの依頼が届く。
ECサイト、病院、SaaS企業、金融機関——あらゆる業界のデータを扱う。
あなたのミッションは、混乱したデータを整理し、
意思決定できる状態に仕上げること。
さあ、最初のクエストが届いた。」
```

### なぜエージェンシー形式なのか

- シナリオをEC・医療・SaaS・金融と無限に拡張できる
- 「仕事の受注」という形式が実務感を生む
- クライアントの要望という形で課題を与えられる
- 難易度・業界を横断した学習ができる

## クエスト設計

### Quest 1: 売上が見えない（ECサイト・初級）

**クライアント**: EC企業「ShopNow」  
**難易度**: 初級  
**推定時間**: 60〜90分  
**データセット**: orders / users / products

**ストーリー**:
```
ShopNowのCTOからメッセージが届いた。
「売上データが各システムにバラバラに存在していて、
先月の売上すら正確に出せない状態です。
経営会議まであと2週間。助けてください。」
```

**ゴール**: 「売上が最も落ちている曜日はどこか？」に答える

---

### Quest 2: 解約率を下げろ（SaaS・中級）

**クライアント**: SaaS企業「TaskFlow」  
**難易度**: 中級  
**推定時間**: 90〜120分  
**データセット**: subscriptions / events / users / plans

**ストーリー**:
```
TaskFlowのCSOから依頼が届いた。
「先月から解約率が急上昇しています。
どのユーザーセグメントで解約が多いのか、
どの機能の利用が少ないのかを分析したい。
LTV・NRR・Churn Rateが見えるMartを作ってほしい。」
```

**ゴール**: チャーン分析基盤を構築し、解約リスクの高いセグメントを特定する

---

### Quest 3: 患者データを守れ（医療・中級）

**クライアント**: 医療機関「CareHub」  
**難易度**: 中級  
**推定時間**: 120分  
**データセット**: patients / diagnoses / treatments / staff

**ストーリー**:
```
CareHubの情報部門から連絡が来た。
「患者データを分析したいが、個人情報保護法がある。
匿名化処理を施しながら、治療効果の分析基盤を作ってほしい。
データ品質が命です。」
```

**特徴**: 匿名化・SCD（Slowly Changing Dimensions）・データ品質チェックを学ぶ

---

### Quest 4: 金融リスクを計算せよ（金融・上級）

**クライアント**: フィンテック企業「FinTrack」  
**難易度**: 上級  
**推定時間**: 180分  
**データセット**: transactions / accounts / risk_events / market_data

**ロック条件**: Lv.5以上 + 中級クエスト2本完了

## ステージ設計詳細

### ステージ共通構造

```typescript
interface Stage {
  id: string;               // 'source' | 'staging' | 'warehouse' | 'mart'
  title: string;            // ステージ名
  gameType: 'rpg' | 'stage_clear' | 'simulation' | 'boss'; // ゲーム形式
  missionText: string;      // ミッション説明
  hintText: string;         // ヒント
  initialSQL: string;       // 初期表示SQL
  validationRules: Rule[];  // 正解判定ルール
  xpReward: number;         // 獲得XP
  badgeId?: string;         // 獲得バッジ
}
```

### AIフィードバックの口調設定

```
上司キャラクター「田中シニアエンジニア」として話す。
- 褒めるときは具体的に褒める
- 指摘するときは理由を説明する
- 改善提案は必ず1つ以上含める
- 口調: 丁寧だが親しみやすい
- 例: 「いいですね！ただ、_loaded_atカラムを追加すると
       監査性が高まります。現場では必須の習慣です。」
```
